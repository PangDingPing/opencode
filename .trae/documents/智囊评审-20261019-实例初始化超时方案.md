## 评审意见

### 🔴 严重问题（必须解决）

**1. S3 方案一的「后续请求自动重连」表述与 ScopedCache 实际语义矛盾**

- **问题**：方案 S3 写「超时后 MCP 状态记为 failed，后续请求按现有 createAndStore 重连逻辑再试」。但 ScopedCache 的实现注释明确 "Successful and failed lookup exits are both cached"：初始化器超时降级返回的空状态是**成功结果**，会被缓存到实例生命周期结束。后续 `InstanceState.get` 直接命中缓存，**不会**重新触发 lookup，`createAndStore` 永远不会被自动调用。
- **影响**：降级后该用户/目录的 MCP 工具在整个实例生命周期内静默不可用（好过挂死，但方案描述的行为不成立），且用户无感知恢复路径。
- **修正**（三选一，按改动量递增）：
  - **1a（最小改动，推荐）**：接受「降级后 MCP 需显式恢复」语义，但必须让用户可感知、可操作——MCP `status()` 已暴露 failed 状态，前端 MCP 设置面板已有状态展示；在方案中把「自动重连」改为「降级后 status=failed 可见于 MCP 面板，用户点连接（`mcp.connect`）或重启实例（configUpdate → disposeAll）即恢复」。
  - **1b**：降级空状态不缓存——超时分支改为 `Effect.fail` 传出一个专用错误，在 `InstanceState.get` 调用处（tools()/prompts() 等）catch 该错误返回空工具。改动面大（多调用点），不推荐。
  - **1c**：降级后安排延迟自动重试（`Effect.sleep + invalidate` 一次），引入新机制，与「不做的事」原则冲突，不推荐。

### 🟡 重要问题（建议解决）

**2. 前端重试循环缺少总上限，存在事件丢失时的无限循环窗口**

- SSE 断线重连窗口内 `init-failed` 事件可能丢失，此时重试循环的唯一终止条件失效——每个请求挂满 120s 后 503，循环理论上无限。
- **修正**：`sendWithInitRetry` 增加总时长上限（建议 15 分钟，覆盖最坏初始化 + 数轮重试），超限后抛出可读错误并停止；横幅同步显示「初始化耗时过长，请稍后重试或联系管理员」。

**3. S1 代码骨架建议直接采用 `Effect.timeoutOrElse`，消除 v4 API 不确定性**

- 方案中的 `Effect.timeout + isTimeoutCause` 需要判别超时标记（方案自己标注「实施时确认」）。实测 effect v4 beta：`Effect.timeout` 失败类型为 `Cause.TimeoutError`（[Effect.d.ts:7586](file:///d:/AI/opencode/node_modules/effect/dist/Effect.d.ts#L7586)），且项目已有 `Effect.timeoutOrElse` 先例。直接改用 `timeoutOrElse` 一步到位，非超时失败原样透传，语义更干净。
- 503 构造同理：用已有先例 `HttpServerResponse.jsonUnsafe(body, { status: 503 })`（[global.ts:174](file:///d:/AI/opencode/packages/opencode/src/server/routes/instance/httpapi/handlers/global.ts#L174)）替代方案的 `raw + bodyJsonSafe` 组合。

**4. 322s 卡死的微观根因仍未插桩确认，S3 的实际防区存疑**

- 单 MCP 连接已有可靠 30s 上限（Promise.race + transport close），失败不致命。串行 N 个 MCP 的最坏等待 = N×30s，用户场景 1-2 个 MCP 时 60s 内。322s 卡死为何没被 30s 砍掉？可能：卡点在 spawn 前置（npx 解析/下载发生在 client.connect 计时外）、`McpCatalog.defs` 无超时、或 plugin.init 慢。方案 24 行已诚实标注，但评审建议**把「实施第一步先插桩定位」升格为 S0**：用最小日志（`InstanceState.make` 初始化器进入/退出时间戳 + 每 MCP create 耗时）跑一次复现，再决定 S3 的必要性。若卡点不在 MCP，S3 是无效防御；无论如何 S1（等待者超时）都成立。
- **折中**：S3 方案一成本极低（3 行），作为「不知道卡点在哪」的兜底仍值得保留——但文档应明确其定位是兜底而非根治。

### 🟢 优化建议（锦上添花）

**5. 503 响应加 `Retry-After` 头**：HTTP 标准语义，前端可读，也利于未来网关/代理行为正确。

**6. S2 事件的 `services-done` 加 `elapsedMs` 属性**：观测各实例初始化服务阶段耗时，为后续容量评估（呼应在线用户审计方案）积累数据。

**7. `init-failed` 的 error 内容脱敏**：多用户部署下 `server.instance.*` 事件广播给所有连接（非会话域事件不过滤），error 字符串可能含路径信息。建议只传 error 类型摘要（如 `"bootstrap failed"`），详情走服务端日志。

## 苏格拉底质疑（交互式）

1. **反思问题**：用户最初的痛点是「会话无反应」，根因（npm 官方源）已修复。本方案防的是「下一次同类故障」——是否应该先问：同类风险的概率还剩多少？（弱网容器、慢插件、新增慢 MCP 均可复现，防御有价值；但若 Docker 环境已固 npmmirror，剩余风险主要是新增 MCP 配置错误场景——S1 的 120s 上限已覆盖其用户侧体验。）
2. **假设检验**：方案假设「超时后 bootstrap 继续跑、重试命中同一 Deferred 即可成功」——已验证成立（fork 在 scope 上独立，等待者中断不影响）。但若 bootstrap 本身挂死（非慢、是死），等待者会每轮 503 后无限重试——问题 2 的重试上限 + `init-failed` 覆盖失败分支后风险可控。
3. **反方视角**：最挑剔的用户会说「我宁愿等 5 分钟也不想要一个初始化失败的提示」——503 + 重试下用户看到的不是失败而是持续计时，横幅语义设计正确；真正要守住的是「不能出现误导性错误文案」，F1 的 `init.failed` 分支文案需明确「环境初始化失败（不是你的消息发送失败）」。

## 改进版方案（S3 修正段）

原 S3 方案一的恢复语义段落替换为：

> 超时降级返回空状态（`emptyState()`，各 server status = `failed: "init timeout"`），该结果会被 ScopedCache 缓存至实例生命周期结束（已验证 ScopedCache 对成功结果照常缓存）。**因此降级后 MCP 工具不会自动恢复**：恢复路径为 a) 用户在 MCP 状态面板看到 failed 后点重连（`mcp.connect` → `createAndStore` 原地更新可变 state，无需 invalidate）；b) 全局配置更新触发实例 dispose 重建。前端 F1 横幅在 `server.instance.ready` 后如检测到 MCP 存在 failed 状态，提示「部分 MCP 服务器未就绪，可在设置中重连」。
