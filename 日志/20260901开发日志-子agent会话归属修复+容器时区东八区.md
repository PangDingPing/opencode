# 20260901 开发日志 - 子 agent 会话归属继承 + 权限空值保护 + 容器时区东八区

## 需求背景

opencode v1.17.6 多用户版（docker v0.1.5，容器 `yejian-v0.1.5`）两个线上问题，用户提供了 opencode.db 数据参考，并要求**先出评估报告、确认后再动手**：

1. **时间是格林尼治时间**：用户处于北京东八区，需要改为东八区。
2. **普通用户打不开子 agent 会话页面**：点击任务卡片跳转至"新建会话"页面；管理员则可正常打开。

## 排查过程

### 问题一：时区

1. 前端时间显示走浏览器本地时区（`session-ui/src/components/message-part.tsx` 的 `Intl.DateTimeFormat`），界面渲染正常——问题不在前端。
2. `docker exec yejian-v0.1.5 date` 显示容器为 **UTC**。影响：system prompt 里的当前日期、服务端日志、默认会话标题时间全部慢 8 小时。
3. 该分支 Dockerfile（多阶段构建，runtime 为 `alpine:3.20`）未设 `TZ`、未装 `tzdata`；实测发现 tzdata 已被 libreoffice 依赖链带入，**只缺 `TZ` 环境变量**——意味着不重建镜像、仅重建容器加 `-e TZ=Asia/Shanghai` 即可立即生效。

### 问题二：子 agent 会话不可见（本次主体）

1. **子 agent 功能本身没有坏**：数据库实测 35 条子会话（`parent_id` 非空）都有标题（如"建筑专业绿建核查 (@general subagent)"）和完整消息记录——task 工具正常创建、执行、产出。
2. 根因是**归属缺失导致的可见性问题**，且是双重不可见：

   | 层面 | 机制 | 普通用户看到的 |
   | --- | --- | --- |
   | 会话列表 | `session.list` 按当前用户过滤 `WHERE user_id = ?`，子会话 `user_id` 为 NULL 不匹配 | 子会话不出现在列表/会话树 |
   | 会话详情 | `requireSession`：`info.user_id !== user.value.id` 恒成立 → 404 → 前端跳"新建会话" | 点任务卡片跳转新建页 |

3. `user_id` 为什么为 NULL：子会话由 task 工具在**服务端内部**创建（`sessions.create`），不经过 HTTP create 接口的 `writeOwnership` 补写逻辑；而实现层 `Session.create` 明明支持 `userID` 入参，只是 `task.ts` 没传 + `Interface.create` 类型声明漏了该字段。
4. 管理员两道关卡都不检查 `user_id` → 能正常打开，反证子 agent 执行链路健康。

## 实施过程

### 1. 存量数据迁移（线上立即生效）

1. **主机沙箱无法直接访问数据库**：Python `sqlite3.connect` 打开 `E:\AI\AIworkbench-data\root\.local\share\opencode\opencode.db` 时对 `-shm` 文件访问被拒。改为把脚本 `docker cp` 进容器、用容器内 python3 执行（数据卷挂载在容器 `/root/.local/share/opencode/`）。
2. **在线一致性备份**：用 `sqlite3` backup API（自动处理 WAL），落盘 `E:\AI\AIworkbench-data\root\opencode.db.bak-20260901`。
3. **预检意外**：评估时 35 条子会话中 34 条 `user_id` 为 NULL，预检时只剩 1 条空（34 条在此期间已被正确设置，推测用户曾操作），无孤儿子会话。
4. **UPDATE 首次失败**：报 `database disk image is malformed`。`PRAGMA integrity_check` 定位到 **`session_user_id_idx` 索引损坏（row 112 缺失）**——主表数据完好，UPDATE 要维护这个索引才报错。
5. **REINDEX 重建索引**（从主表重新生成、无损），完整性检查恢复 `ok`，重跑 UPDATE 成功。
6. **迁移结果**：35 条子会话全部归属正确（usr_庞定平 × 34、usr_贺俊毅 × 1）。`session.get` 每次直查库无缓存，**迁移即时生效，无需重启容器**。

## 关键设计决策

1. **fail-closed 而非 fail-open**：requireSession 对空 `user_id` 一律拒绝普通用户。dev 分支上游的语义是"空值放行"，但存量已迁移完毕、新子会话已继承归属，fail-closed 可防止未来异常产生的无主会话对所有登录用户可见（越权风险）——是有意与上游不同的更安全选择。
2. **迁移加保护条件**：UPDATE 仅当父会话确有有效归属时才继承（`EXISTS` 子查询），避免孤儿/无主父会话把 NULL 再传播一遍。
3. **两段式生效**：数据迁移 + 容器 TZ 重建让线上**立即**恢复正常；代码修复沉淀在分支里，等下次例行重建镜像时自然带上，无需紧急发版。

## 踩坑记录

1. **索引损坏伪装成库损坏**：`database disk image is malformed` ≠ 主表数据损坏，`integrity_check` 会精确指出是哪个索引哪一行；先 `REINDEX` 修复索引再操作，避免不必要的恢复动作。推测损坏与容器迁移/异常退出有关。
2. **主机沙箱不能直接开线上库**：WAL 模式的 `-shm`/`-wal` 文件访问被拒；数据库操作一律进容器内用 python3 执行（python3/alpine 容器自带）。
3. **实际容器配置 ≠ 脚本模板**：重建容器前必须 `docker inspect` 提取真实挂载/env/cmd，照 `build.ps1` 模板重建会把数据卷挂错。
4. **带中文的 .ps1 脚本执行失败**：PowerShell 5 按 ANSI 解析无 BOM 的中文脚本导致语法错误；脚本文件一律英文书写。
5. **PowerShell 不支持 `&&`**：多命令用 `;` 分隔；`git fetch` 需 `-c http.sslVerify=false` 单命令跳过证书校验（本机代理拦截 HTTPS）。
6. **stash 可跨分支精确恢复文件**：`git checkout stash@{0} -- <path>` 比 `stash pop` 更适合"在错误分支做了改动"的纠错场景——先确认两分支间该文件无差异再恢复。
7. **线上库预检数字会漂移**：评估时的 35 条 NULL 到实施时只剩 1 条（期间被设置）；任何迁移脚本都要**实施时重新预检**，不能信报告里的旧数字。
