## 需求背景

管理员需要"知道谁在用"：能查看当前活跃用户并踢下线，能追溯登录/登出/登录失败/被踢/被禁用事件。三个交付物：

| 功能 | 内容 |
| --- | --- |
| A 在线用户页面 | 活跃判定 = 最近 15 分钟内有请求（基于 `session_token.last_extend_at` 既有机制，**无新增心跳**），admin 专属，带「踢下线」按钮 |
| B 登录审计 | `login`/`logout`/`login_failed`/`kicked`/`disabled` 五类事件 → DB 表 + 按天 JSONL 日志文件 + 容器控制台三路输出 |
| C 容量评估报告 | 纯分析不改代码，输出到会话回复（见本日志末尾） |

已确认设计决策（2026-10-12 评审）：审计不做防篡改外发（接受可篡改性）；"知道谁在用"即可；在线页带踢下线；禁用与踢下线分开记录。

## 备选方案

- **活跃判定**：新增心跳机制 vs 复用 `last_extend_at`。选后者——零新增请求、零写放大；语义上「在线 = 活跃」，页面底部注明，不误报"挂着页面也算在线"。
- **审计存储**：仅 DB vs DB + JSONL 双写。选双写——DB 供筛选分页查询，JSONL 供 grep/备份；两路均 best-effort 吞错，不影响登录主流程。
- **迁移生成**：官方 `script/migration.ts` vs 手写迁移。选手写——官方脚本依赖 schema.json snapshot 与 drizzle 定义 diff，但 snapshot 落后于 m35/m36 手写迁移（不含 user/session_token 表），跑它会打包出错误迁移（见踩坑 2）。

## 影响范围

- 全部新功能走新文件；上游文件改动集中、带 `// yejian:` 注释，合并冲突面最小
- 登录/登出/踢下线/禁用路径各加一次审计写（SQLite insert + JSONL append），best-effort 吞错不影响主流程
- `getRequestIP` 增强使登录限速与 token 记录的 IP 更准（反向代理场景才有差异）

## 踩坑记录

1. **`DatabaseMigration.apply()` 双路径——fresh-install 不含 fork 自定义表（测试 `no such table: auth_audit`）**：对空库（`:memory:`）走 `schema.up()`（schema.gen.ts **仅上游表**）+ 标记全部迁移完成**不执行**；仅当已存在 `session` 表才走 `applyOnly(db, migrations)` 逐个执行。测试里 `Database.layerFromPath(":memory:")` 永远走 fresh 路径 → user/session_token/auth_audit 全缺。修复：测试手动构建 `databaseLayer = Layer.effect(Database.Service, ...applyOnly(db, migrations).pipe(Effect.orDie))`。**本 fork 一直只支持「老库升级」路径**——是 fork 现状非本次引入，后人写测试勿走 layerFromPath fresh 路径。
2. **官方迁移生成脚本在本 fork 不可用**：`script/migration.ts` 依赖 schema.json snapshot 与 drizzle 表定义 diff，snapshot 落后于 m35/m36 手写迁移（无 user/session_token 表），跑它会打包出错误迁移。fork 自定义表迁移一律**手写迁移文件 + 手动注册 migration.gen.ts**。
3. **core/package.json exports 通配陷阱**：`./*: ./src/*.ts` 只映射单段文件不含目录 index（`./auth-audit` 会错映射到不存在的 `src/auth-audit.ts`），目录模块必须像 auth-token 先例一样显式加两行 exports。
4. **Effect 4 的 `Scope` 是值命名空间**：类型引用必须 `Scope.Scope`，直接拿 `Scope` 作类型报 TS2709；组合层带 Scope 需求时 run 签名需显式声明并用 `as Effect.Effect<A, E, never>` 断言收窄（否则泛型推断报 `Exclude<R, Scope> not assignable to never`）。
5. **HttpApiEndpoint GET query 参数**：用 `query:` 字段声明（不是 payload），数字参数需 `Schema.NumberFromString`（URL query 全是字符串），handler 里 `ctx.query` 读取。
6. **PowerShell 5.1 不支持 `&&`**：链式命令报 ParserError，改用 `;`。

## 功能 C：Docker 容量评估报告（纯分析）

**架构事实**：单 Bun 进程（binary）+ `node:http`；effect fiber 每请求一纤程；SQLite WAL（busy_timeout 5000ms，named volume ext4，写吞吐千级 TPS）；LLM 流量是外部 API 代理（容器 CPU 占用低）；每浏览器页面 1-2 条 SSE 长连接（心跳 10s）；`GlobalBus.setMaxListeners(200)`；容器无 `--memory/--cpus` 限制。

**瓶颈排序**：
1. SSE 连接上限（代码级天花板，最先到）：GlobalBus 200 监听器 → 人均 2-3 条连接 → 约 60-100 个并发浏览器页面
2. 单进程 CPU：流式 JSON 解析 + SSE 广播扇出在单线程，多用户同时收长回复时是热点，无法纵向扩容
3. SQLite 单写者：50 人规模余量大，100+ 活跃对话时排队（busy_timeout 5s 兜底）
4. 无容器资源隔离：内存挤占宿主机风险

**结论**：当前 32 账号、日常 ≤10 同时活跃——余量充足（估计可承载约 50 活跃用户）；100+ 需调 GlobalBus 上限 + 加资源限制；再往上需多实例（上游已留 clustering 预留）。
