# docker 镜像 v0.1.8 重建 + 启动命令统一（build.ps1 / run.ps1 / readme）

## 需求背景

- 用户要求参考 `docker/readme.md` 重建 docker 镜像，版本号 v0.1.8
- 同时给出新的标准启动命令，与旧命令相比两处变化：
  1. **新增 `/YEJIAN2` 工作区挂载**：`-v "E:\AI\YEJIAN2:/YEJIAN2"`
  2. **不再注入 `--env-file`**（API key 环境变量默认不带）
- 此前 `build.ps1` 默认值停留在 v0.1.7、`run.ps1` 停留在 v0.1.6 且都没有 YEJIAN2 挂载，脚本默认启动命令与用户实际命令长期不一致，每次都要手动传参，容易出错——本次一并对齐

## 备选方案

- **构建模式选择**：改了源码（本次会话前的 serve.ts 类型修复等），按 readme 推荐用 `-RebuildBuilder`（builder 阶段重编 binary，runtime 全缓存，实测约 1 分钟）；`-ForceRebuild` 全量重建 1-2 小时没必要；默认全缓存会复用旧 builder 层拿到旧二进制，更不行
- **readme 的快速开始章节**：原文推荐改 web UI 用 `-ForceRebuild`，与"利用缓存构建"章节自相矛盾（多阶段构建下 binary 在 builder 层编译，源码变更应重编 builder 层）。本次以 `-RebuildBuilder` 为准修正了快速开始章节
- **run.ps1 的 `-EnvFile` 默认值**：原默认指向 `E:\AI\dockerimage\api-keys-v0.0.8.env`；用户标准命令不含 env-file，故默认改为空串（不注入），需要时传参保留 `-EnvFile` 能力

## 影响范围

- **容器编排层**：`build.ps1` / `run.ps1` 默认值变化只影响今后启动的容器；本次启动的 `yejian-v0.1.8` 已按新命令运行并验证
- **API key 不再默认注入**：容器内无 API key 环境变量（与 v0.1.7 现状一致——v0.1.7 用的 api-keys-v0.0.8.env 也未设 OPENCODE_SERVER_PASSWORD，web 一直处于无密码状态，内网可接受）。需要时启动加 `--env-file` 或脚本传 `-EnvFile`
- **旧容器/镜像未清理**：`yejian-v0.1.7` 容器（Exited）与镜像保留，确认 v0.1.8 稳定后可删
- **镜像内容零变化**：Dockerfile 未动，v0.1.8 与 v0.1.7 的镜像层差异仅为 builder 阶段重编的二进制（源码为最新 dev 状态）

## 踩坑记录

1. **后台任务误报构建失败（exit code 1）**：`build.ps1 -RebuildBuilder` 后台跑完报 failed，日志末尾实际是「TRAE Sandbox Error: hit restricted — Not allow operate files: docker-desktop.exe.log」——沙箱拦截 Docker 日志读取，构建和容器启动本身全部成功（日志里有 `Container Started Successfully`）。教训：后台任务 failed 先看日志尾部再定性，别急着重跑
2. **PowerShell 5 不支持 `&&` 和 heredoc**：`git add ... && git commit -m "$(cat <<'EOF' ...)"` 直接 ParserError（token '&&' not valid / '<<' reserved）。改用 `;` 分隔 + 多个 `-m` 参数（git 自动以空行拼接）传 commit message 与 Co-Authored-By 尾注
3. **serve.ts 幻影改动**：`git status` 显示 M 但 `git diff` 为 0 行——`.gitattributes` 的 `* text=auto eol=lf` 换行符规范化产物，无内容变化，无法也不需要提交；下次该文件有真实改动时自然消失
4. **readme 的 `-ForceRebuild` 说法过时**：多阶段构建后 binary 在 builder 层编译，"复用 packages/opencode/dist/ 现成二进制"是 v0.0.6 前的单阶段老流程；源码变更正确姿势是 `-RebuildBuilder`
