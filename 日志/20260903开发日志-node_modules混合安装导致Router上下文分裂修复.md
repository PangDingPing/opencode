# 20260903 开发日志：node_modules 混合安装导致 Router 上下文分裂（subagent 前端报错修复）

## 需求背景

本地启动前后端 dev 服务后，启动 subagent 必现报错：

```
Error: <A> and 'use' router primitives can be only used inside a Route.
    at useRouter (.../@solidjs/router/dist/routing.js)
    at useLocation (...)
    at render (.../packages/ui/src/components/message-part.tsx:1909)
```

报错位置是 ui 包 `message-part.tsx` 中 task 工具注册的 `render()` 函数内的 `useLocation()` 调用（源码 L1788，Vite 服务端视图 L1909）。用户要求深入分析原因。数据库（`C:\Users\fun2k\.local\share\opencode\opencode-local.db`）无任何异常，问题纯在前端模块加载层。

## 排查过程（根因分析）

### 1. 排除法逐步收窄

- **排除 Virtua 虚拟列表丢上下文**：错误栈里 `untrack(() => component(props))` 是 Solid `Dynamic` 的正常渲染路径
- **排除双 solid-js 实例**：抓取 Vite 服务端返回的 router 模块代码，其内部 `import "solid-js"` 已被改写为预构建实例 `/node_modules/.vite/deps/solid-js.js?v=8765d9f9`，全站唯一
- **修正一个误报**：此前注入式诊断脚本用 `Object.keys(owner.context)` 判断"owner 链上无任何 context"——但 Solid 1.9 的 context id 是 **Symbol**（`createContext` 内 `Symbol("context")`），`Object.keys` 根本看不到。实际 owner 链上是有 context 的

### 2. 关键证据：同一依赖、两个 URL

直接对比 Vite dev server 实际返回的两个源文件的 import 语句：

| 源文件 | `@solidjs/router` 实际解析到 |
|---|---|
| `packages/app/src/app.tsx`（挂载 `<Router>` 一方） | `/@fs/D:/AI/opencode/node_modules/@solidjs/router/dist/index.jsx`（**顶层实体目录**） |
| `packages/ui/src/components/message-part.tsx`（调用 `useLocation` 一方） | `/@fs/D:/AI/opencode/node_modules/.bun/@solidjs+router@0.15.4+95b571dd5236cc92/...`（**.bun 存储另一份**） |

### 3. 文件系统验证

- 根目录 `node_modules\@solidjs\router`：普通实体目录（2026/6/25 创建）
- `packages\ui\node_modules\@solidjs\router`：符号链接 → .bun 存储
- `packages\app\node_modules\@solidjs\router`：**不存在** → import 沿目录树向上命中根目录实体副本
- 根目录共残留 **1437 个实体包目录 + 约 60 个 `.old-*` 残骸**（6/25 的旧安装），与 7/4 的 .bun 隔离安装叠加

### 4. 根因链条

历史安装方式变更（先 isolated linker、后 bunfig.toml 改 `linker = "hoisted"`）造成混合状态 → `@solidjs/router` 磁盘上两份物理文件 → Vite 视为两个模块 → 两份 `RouterContextObj`（各自由 `createContext()` 生成、Symbol id 不同）→ app 用实例 A 提供 context、ui 的 `useLocation` 拿实例 B 查找 → 永远找不到 → 抛错。**`useData` 不报错**是因为其 Provider 和消费者都在 ui 包内用同一份模块。近期 git pull 删除根目录 bun.lock + 重装 + Vite 缓存重建把一直存在的分裂状态暴露出来。

## 踩坑记录

1. **诊断双实例的标准手法**：用 `Invoke-WebRequest http://localhost:3000/@fs/<源文件路径>` 抓 Vite 实际服务出来的 import URL，对比两个消费方是否指向同一物理文件。比看 node_modules 目录结构更直接
2. **Solid context 是 Symbol key**：`Object.keys(owner.context)` 看不到 context，诊断脚本会误报"无任何 context"，要用 `context.id` 直接访问
3. **PowerShell Remove-Item 对个别文件报 ArgumentException**（`@solidjs/start/dist/client/spa/index.jsx`，ACL 正常、无只读属性、无进程占用却拒绝访问）：先 `Rename-Item` 成功证明不是锁，最后 `[System.IO.Directory]::Delete(path, $true)` 一次删干净。遇到删不掉的残留可先试 .NET API
4. **bun install 在沙箱内跑 postinstall 会被拦**：第一次安装 2280 包成功但 29 个工作区链接（@opencode-ai/*）失败（postinstall 脚本写 Windows 系统路径被沙箱拦截）；**重跑一次 `bun install` 7 秒补齐全部链接**。判断依据：日志里 `ENOENT: failed linking dependency/workspace` 全是 workspace 包
5. **验证虚拟列表页面要滚动**：Virtua 只渲染视口内的行，task 消息在会话中部，必须把 `.scroll-view__viewport` 滚到顶部才会渲染；否则 task 卡片计数 0 会误判为修复失败
6. **登录前的 401 是正常噪音**：验证脚本里先 goto 首页再登录，初始请求 `/api/auth/me`、`/global/config` 等必然 401，不要误判为认证问题
