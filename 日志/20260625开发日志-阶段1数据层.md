# 阶段 1：数据层（用户表 + 认证令牌表 + 所有权字段 + 白名单）

## 需求背景

多用户系统改造阶段 1。目标：建立数据层基础，包括用户表（user）、认证令牌表（session_token），为 session 和 credential 表添加 user_id 所有权字段，建立实名白名单机制，并创建初始用户迁移。

## 备选方案

1. **密码哈希算法选择**
   - 方案 A：bcrypt
   - 方案 B（采用）：argon2id（OWASP 2024 推荐）。使用 `@node-rs/argon2` 原生绑定，性能优于纯 JS 实现

2. **白名单存储方式**
   - 方案 A：数据库表
   - 方案 B（采用）：纯文本文件 `docker/allowed-names.txt`。方便管理员直接编辑，无需数据库操作；通过 `allowed-names.ts` 读取并缓存

3. **user_id 列的可空性**
   - 方案 A：NOT NULL（强制每个 session/credential 都有 owner）
   - 方案 B（采用）：可空。历史数据（升级前创建的 session）user_id 为 NULL，归属 `_legacy_system` 用户；新创建的必须填 user_id

4. **初始用户创建方式**
   - 方案 A：手动逐个创建
   - 方案 B（采用）：migration 批量从白名单创建，用 `INSERT OR IGNORE` 保证幂等。密码统一为 "12345678" + must_change_password=1，首次登录强制改密

## 文件改动

### 1. 新建 `packages/core/src/user/sql.ts`
- 定义 `UserID` 品牌类型（Schema.String + brand("UserID")）
- 定义 `UserTable`：
  - `id: text().primaryKey()` — 用户 ID
  - `username: text().notNull().unique()` — 实名（白名单制）
  - `password_hash: text().notNull()` — argon2id 哈希
  - `role: text().notNull()` — "admin" | "user"
  - `display_name: text()` — 显示名（可选）
  - `disabled: integer().notNull().default(0)` — 禁用标志
  - `must_change_password: integer().notNull().default(0)` — 首次登录强制改密
  - `created_at: integer().notNull()` — 创建时间
  - `updated_at: integer().notNull()` — 更新时间

### 2. 新建 `packages/core/src/auth-token/sql.ts`
- 定义 `SessionTokenTable`：
  - `id: text().primaryKey()` — 32 字节随机 token（base64url）
  - `user_id: text().notNull()` — 关联用户
  - `expires_at: integer().notNull()` — 过期时间（7 天 TTL）
  - `last_extend_at: integer()` — 最后续期时间（惰性续期用）
  - `revoked_at: integer()` — 撤销时间
  - `created_at: integer().notNull()`
  - `user_agent: text()` — 用户代理
  - `ip: text()` — 登录 IP

## 影响范围

- **数据层基础**：建立了用户和认证令牌的数据结构，后续阶段的认证逻辑都基于这些表
- **所有权隔离**：session 和 credential 表的 user_id 列为阶段 3 的业务隔离提供基础
- **实名白名单**：限制只有白名单内的实名才能注册，管理员通过编辑文本文件管理白名单
- **历史数据兼容**：升级前创建的 session 归属 _legacy_system 用户，不影响现有使用
