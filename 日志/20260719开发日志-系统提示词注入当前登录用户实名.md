# 20260719 开发日志 - 系统提示词注入当前登录用户实名

## 需求背景

项目已采用实名认证登录（admin 账号 `yejian`，业务用户从 `docker/seed-users.json` 预置 31 个实名账号）。会话输出文件需要放在用户实名文件夹内（如 `0上官兵/`、`1庞定平/` 等）或用实名命名产物。

**痛点**：用户每次开会话都要在提示词框手动输入"我是上官兵"才能让大模型知道身份，繁琐且易忘。

**目标**：让大模型在每次会话中**自动**知道当前登录用户身份，无需用户在提示词框输入名字。主对话和所有子代理（plan/explore/general/task）全部继承。

## 备选方案

- **方案 A（采用）**：在 SessionPrompt.loop 拼装 system prompt 时，根据 `session.user_id` 从 User 表查出实名信息，作为 `<current_user>` 块追加到 system prompt 末尾。优点：主对话和所有子代理都用同一份 system prompt，自动继承；缺点：每次 loop 都查一次数据库（可接受，User 表小且带索引）。
- **方案 B（否决）**：在 Config 里加全局 current_user 字段，所有 SessionPrompt 共享。缺点：Config 是全局的，多用户并发会互相覆盖。
- **方案 C（否决）**：前端在发消息时把用户名塞进 message parts。缺点：子代理不继承，且用户可伪造。

**`packages/opencode/src/session/user-context.ts`**（31 行）

纯函数模块，把 `UserInfo` 格式化成 system prompt 片段：

```ts
export function formatUserContext(user: UserInfo): string {
  const display = user.display_name ?? user.username
  return [
    "<current_user>",
    `  username: ${user.username}`,
    `  display_name: ${display}`,
    `  role: ${user.role}`,
    `  user_id: ${user.id}`,
    "  当需要按用户实名命名输出文件、目录、报告、邮件等产物时，必须使用上面的 display_name（实名）作为标识。",
    "</current_user>",
  ].join("\n")
}
```

不依赖任何 Effect Service，纯函数，便于测试和复用。

## 踩坑记录

### 坑 1：`Service not found: @opencode/UserService`

**现象**：后端启动后发消息报 `Service not found: @opencode/UserService (defined at D:\AI\opencode\packages\core\src\user\index.ts:56:38)`

**根因**：只在 `SessionPrompt.layer` 内 `yield* User.Service`，但 `User.defaultLayer` 没在顶层 `AppLayer` 和 `SessionPrompt.defaultLayer` 内部的 `Layer.mergeAll` 里提供。Effect 的 Layer 是有作用域的，Service 必须在所有使用它的 Layer 作用域内提供。

**修复**：在 4 个 Layer 组合点都补上 `User.defaultLayer` / `User.node`：
1. `app-runtime.ts` 的 `AppLayer`（顶层）
2. `control-plane/workspace.ts` 的 `defaultLayer` 和 `node`
3. `httpapi/server.ts` 的 `LayerNode.make`
4. **关键**：`SessionPrompt.defaultLayer` 内部的 `Layer.mergeAll`（L1600 那个，不是外层链式 `Layer.provide`）

**教训**：Effect Layer 组合不是"只要顶层提供就行"，每个 `Layer.mergeAll` 都是一个独立作用域，内层 `yield*` 需要的 Service 必须在内层 mergeAll 里提供，或者在能透传到内层的外层 provide。

### 坑 2：`SQLiteError: no such column: replacement_seq`

**现象**：发消息后页面转圈圈无回复，后端终端**无任何日志输出**（即使加了 `console.log` 在 handler 入口）。前端控制台显示 `POST /session/.../prompt_async Fetch failed loading`。

**排查过程**：
1. 最初怀疑请求没到后端（vite 代理问题、cookie 失效）——但 `POST /session` 成功说明代理通
2. 在 `promptAsync` handler 入口加 `console.log("[yejian-debug] promptAsync handler ENTERED")`，重启后端，发消息——**这次日志打印了**，说明请求到了 handler
3. 日志显示 `prompt_async FAILED: SQLiteError: no such column: replacement_seq`，问题定位到数据库 schema

**根因**：数据库被更高版本（带 `simplify_session_context_epoch` 迁移）的 opencode 跑过，`session_context_epoch` 表只有 4 列（session_id/baseline/snapshot/baseline_seq），缺 `replacement_seq` 和 `revision` 两列。但当前 `v.1.17.6多用户` 分支的代码 `context-epoch.ts` 还在查询这两列，导致 prompt_async 直接报 SQLite 错误失败。

**为什么之前后端无日志**：旧后端进程（PID 12692，12:16:26 启动）是在我加 debug 日志**之前**启动的，加载的是旧代码，所以即使请求到了 handler 也不会打印 debug 日志。重启后端加载新代码后才看到日志。

**修复**：用户选择删库重置。手动删除 `C:\Users\fun2k\.local\share\opencode\opencode-local.db*` 后重启后端，数据库从迁移脚本重建，包含完整的 `replacement_seq` 和 `revision` 列。

**教训**：
- "后端无日志"不等于"请求没到后端"，可能是后端加载的是旧代码——重启后端是排查的第一步
- 数据库 schema 不匹配是版本不匹配的常见症状，特别在分支切换/上游合并后
- `simplify_*` 类迁移是**不可逆**的（删列），降级到旧代码时必须重建数据库

### 坑 3：`session.userID` 字段名错误（snake_case vs camelCase）

**现象**：数据库修复后，发消息能正常回复，但大模型仍然说"我不知道用户的姓名"，让用户输入名字。后端 debug 日志显示 `session.userID = undefined`。

**根因**：我在 [prompt.ts:1346](file:///d:/AI/opencode/packages/opencode/src/session/prompt.ts#L1346) 写的是 `session.userID`（camelCase），但 [Session.Info Schema](file:///d:/AI/opencode/packages/opencode/src/session/session.ts#L228) 定义的字段名是 `user_id`（snake_case）：

```ts
// session.ts L220-241
export const Info = Schema.Struct({
  ...
  user_id: optionalOmitUndefined(UserID),  // ← snake_case
  ...
})
```

而 `CreateInput`（L257-267）里又是 `userID`（camelCase）：

```ts
export const CreateInput = Schema.optional(
  Schema.Struct({
    ...
    userID: Schema.optional(UserID),  // ← camelCase
  }),
)
```

`Session.create`（L564-576）把 `input.userID` 写到 `result.user_id`，所以 Info 对象里字段名是 `user_id`。

**修复**：`session.userID` → `session.user_id`，同时清理 debug 日志。

**教训**：
- 这套代码 schema 字段命名不统一：数据库列名和 Info Schema 用 snake_case，CreateInput 用 camelCase。容易混淆
- 加 debug 日志是排查"逻辑没走到"类 bug 的最快方法——`console.log` 比 Effect 的 `Effect.logInfo` 更直接，能在终端立刻看到
- 字段名 bug 不会报错，只会让 if 条件永远 false，业务逻辑静默跳过——debug 日志能立刻暴露

## 已知遗留

1. **Context 标签页不显示 `<current_user>` 块**：注入发生在 SessionPrompt 层的 `system` 数组，不在 SystemPrompt 模块范围内。如需在 Context 标签页显示，需要在 SystemPrompt 模块加一个 `currentUser()` 方法——但本次需求是"让模型知道"，不是"让用户看到"，不做
2. **每次 loop 都查一次 User 表**：`userService.getUser(session.user_id)` 每次 prompt 都执行。User 表小（< 100 行）且带主键索引，性能可接受。如需优化可在 SessionPrompt.layer 内加 LRU 缓存——但本次不做，避免过度工程
3. **`<current_user>` 块在 system prompt 末尾**：放在 env/instructions/skills 之后。如果上游有 `STRUCTURED_OUTPUT_SYSTEM_PROMPT` 之类的追加，`<current_user>` 会在它们之前。当前顺序符合预期
4. **数据库 schema 不匹配风险**：本次遇到的 `replacement_seq` 缺失是分支切换导致的。合并上游时如果上游有新的 simplify 迁移，需要重新评估是否降级数据库
