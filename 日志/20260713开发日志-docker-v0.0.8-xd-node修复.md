# Docker v0.0.8 镜像构建：xd.node undefined 修复 + 密码验证修复 + 数据清理

## 需求背景

v0.0.8 镜像（多阶段构建，Linux 容器内编译 binary）构建成功后，连续发现 3 个运行问题，本日志按时间顺序记录：

1. **xd.node undefined 错误**：容器启动报 `TypeError: undefined is not an object (evaluating 'xd.node')`
2. **verify is not defined 错误**：xd.node 修复后又报 `ReferenceError: verify is not defined`
3. **密码 hash 格式不匹配**：登录永远 401，旧数据库用户的密码 hash 是 PHC 格式 `scrypt$N=..$r=..$p=..$salt$hash`，但 `verifyPasswordHash` 只识别冒号格式 `salt:hash`

外加一个 **bootstrapUsers 不工作** 现象（详见末尾"已知遗留"）：`serve.ts` 的 `bootstrapUsers()` 在编译后的 binary 中没有创建用户，user 表始终为空，docker logs 也无任何 bootstrap 输出。

## 备选方案

### 方案 A：恢复自引用命名空间导出（✅ 采用 修复 1）

把 `export const Xxx = { Service, defaultLayer, node }` 改回 `export * as Xxx from "..."` 自引用命名空间导出。

理由：
- v0.0.3（能运行）用的就是 `export * as Database from "./database"` 模式
- `global.ts:88` 也用这个模式（`export * as Global from "./global"`），且在 v0.0.8 中正常工作
- 自引用命名空间导出创建 live binding namespace 对象，namespace 对象本身始终存在，属性在模块体执行后填充

### 方案 B：延迟求值 node 属性

将 `node` 属性改为延迟求值，避免模块加载时调用 `path()`。

否决理由：治标不治本，如果 `Database` 对象本身是 undefined（因 lazy loading 顺序），延迟求值 `node` 也无济于事。

### 方案 C：确保依赖正确声明

检查 Bun 打包配置，确保模块依赖正确追踪。

否决理由：Bun compile 的 lazy loading 是内部行为，无法通过配置控制。

### 方案 D：手动改密码并保留兼容（✅ 采用 修复 3）

- `hashPassword` 改为生成 PHC 格式 `scrypt$N=..$r=..$p=..$salt$hash`（与旧数据兼容）
- `verifyPasswordHash` 同时支持 PHC 格式和冒号格式
- 优点：新生成和旧数据都能验证；缺点：函数实现略复杂

### 方案 E：清空数据库重新创建（✅ 采用 修复 3 续）

旧数据库 32 个用户的密码 hash 都是 PHC 格式但无法匹配 `Yejian2016` 等常见密码。**直接清空数据目录**，让容器内数据库从空库开始。手动用 Python 脚本生成新 hash 并插入用户。

## 根因分析

### 修复 1 根因：xd.node undefined

合并提交 `859f44c3e` 删除了自引用命名空间导出 `export * as Database from "./database"`，改成了 `export const Database = { Service, defaultLayer, node }`。

**两种导出方式的差异**：

| 导出方式 | Bun compile 行为 | 结果 |
|----------|-----------------|------|
| `export * as Database from "./database"` | 创建 live binding namespace 对象，namespace 对象本身始终存在 | ✅ `Database` 不会是 undefined |
| `export const Database = { Service, defaultLayer, node }` | 常量值导出，在模块体 lazy 函数执行时才赋值 | ❌ 模块体未执行时 `Database` 是 undefined |

Bun compile 把每个模块编译成 lazy 函数，在首次访问时调用。如果模块 A 引用模块 B 的导出，但模块 B 的 lazy 函数还没调用，模块 B 的 `export const` 导出就是 undefined。

### 修复 2 根因：verify is not defined

`user/index.ts` L142 的 `verifyPassword` 函数体内调用了 `verify(password)`，但文件里只定义了 `verifyPasswordHash` 函数（无参数重载）。原代码：

```typescript
const valid = yield* Effect.promise(() => verify(row.password_hash, password))
```

调用的是不存在的 `verify` 函数，而 `verifyPasswordHash` 的签名是 `(stored: string, pwd: string)`，参数顺序正确。修复：调用名改为 `verifyPasswordHash`。

### 修复 3 根因：密码 hash 格式不匹配

`hashPassword`（v0.0.6 引入的 scrypt 替代）生成冒号格式 `saltHex:hashHex`：

```typescript
// 原 hashPassword
const salt = randomBytes(16)
const hash = scryptSync(pwd, salt, SCRYPT_PARAMS.keylen, ...)
return `${salt.toString("hex")}:${hash.toString("hex")}`
```

但旧数据库中 32 个用户的密码 hash 是 PHC 标准格式 `scrypt$N=16384$r=8$p=1$saltHex$hashHex`（外部工具生成），`verifyPasswordHash` 解析时按冒号 split 得到 6 段，认为 `saltHex` 是 `scrypt$N=16384$r=8$p=1$saltHex`，`hashHex` 是 `hashHex`，用错误的 salt 重新计算 hash，自然永远不匹配。

修复：让 `hashPassword` 也输出 PHC 格式；让 `verifyPasswordHash` 同时识别 PHC 和冒号两种格式（按 `startsWith("scrypt$")` 判断）。

```typescript
// 生成 PHC 标准格式 "scrypt$N=..$r=..$p=..$saltHex$hashHex"，与外部工具兼容
export function hashPassword(pwd: string): Promise<string> {
  return new Promise((resolve, reject) => {
    try {
      const salt = randomBytes(16)
      const hash = scryptSync(pwd, salt, SCRYPT_PARAMS.keylen, {
        N: SCRYPT_PARAMS.N,
        r: SCRYPT_PARAMS.r,
        p: SCRYPT_PARAMS.p,
      })
      resolve(`scrypt$N=${SCRYPT_PARAMS.N}$r=${SCRYPT_PARAMS.r}$p=${SCRYPT_PARAMS.p}$${salt.toString("hex")}$${hash.toString("hex")}`)
    } catch (e) {
      reject(e)
    }
  })
}
```

**改动 C**（L32-67，verifyPasswordHash 支持双格式）：
```typescript
function verifyPasswordHash(stored: string, pwd: string): Promise<boolean> {
  return new Promise((resolve, reject) => {
    try {
      // 支持两种格式：
      // 1. 本项目 hashPassword 生成的 PHC 格式 "scrypt$N=..$r=..$p=..$saltHex$hashHex"
      // 2. 旧冒号格式 "saltHex:hashHex"（外部工具早期版本）
      let saltHex: string
      let hashHex: string
      let params = { N: SCRYPT_PARAMS.N, r: SCRYPT_PARAMS.r, p: SCRYPT_PARAMS.p }
      if (stored.startsWith("scrypt$")) {
        // PHC 格式：scrypt$N=..$r=..$p=..$salt$hash
        const parts = stored.split("$")
        for (let i = 1; i <= 3; i++) {
          const [k, v] = parts[i]!.split("=")
          if (k === "N") params.N = Number(v)
          else if (k === "r") params.r = Number(v)
          else if (k === "p") params.p = Number(v)
        }
        saltHex = parts[4]!
        hashHex = parts[5]!
      } else {
        // 冒号格式：saltHex:hashHex
        const parts = stored.split(":")
        saltHex = parts[0]!
        hashHex = parts[1]!
      }
      if (!saltHex || !hashHex) return resolve(false)
      const salt = Buffer.from(saltHex, "hex")
      const expected = Buffer.from(hashHex, "hex")
      const actual = scryptSync(pwd, salt, expected.length, params)
      resolve(actual.length === expected.length && timingSafeEqual(actual, expected))
    } catch (e) {
      reject(e)
    }
  })
}
```

## 踩坑记录

1. **`xd` 是 minify 后的变量名，无法直接搜索**：通过 binary strings 提取 `xd.node` 附近上下文，发现 `xd={Service:n0,defaultLayer:N$,node:H9}`，确认 `xd` = `Database`

2. **PowerShell `$` 变量解析问题**：在 PowerShell 中执行 docker 命令时，`$bunfs` 被 PowerShell 当作变量解析。解决方法：把诊断命令写入 `.sh` 文件，挂载到容器内用 `sh /debug.sh` 执行

3. **`export const Xxx = {...}` 在 Bun compile 后有 lazy loading 问题**：Bun compile 把每个模块编译成 lazy 函数，`export const` 导出在模块体函数执行时才赋值。如果模块体函数还没调用，导出就是 undefined。自引用命名空间导出 `export * as Xxx from "..."` 创建的 namespace 对象是 live binding，始终存在

4. **错误信息 `Bun v1.3.14 (Linux x64 baseline)` 的误导**：build.ts 选择的是 AVX2 目标（`avx2 === undefined`），但错误信息说 baseline。这是因为 `bun-linux-x64-musl` target 在 Bun 中默认就是 baseline，与 build.ts 配置无关

5. **PowerShell `Remove-Item -Recurse -Force` 删除 Docker 创建的文件失败**：报大量文件锁/sandbox 限制错误。解决方法：用 `docker run --rm -v "E:\AI\AIworkbench-data:/data" alpine:3.20 sh -c "rm -rf /data/* /data/.*; mkdir -p /data/root /data/tmp"` 在容器内清理

6. **PowerShell heredoc / 引号转义问题**：在 PowerShell 中执行 `docker exec ... sh -c "python3 << 'EOF' ..."` 引号冲突。解决方法：将 Python 脚本写入 `.py` 文件，用 `docker cp` 复制到容器后执行

7. **运行中的 opencode 进程持有 SQLite 锁**：用 Python 脚本直接连主库报 `unable to open database file`。解决方法：先 `docker stop yejian-AIworkbench`，再用临时容器挂载宿主机目录后访问数据库

8. **NTFS 卷挂载导致 SQLite 临时文件创建失败**：容器内 `sqlite3 /root/.local/share/opencode/opencode.db` 报 `unable to open database file`（连只读 mode 都失败），但 `cp` 到 `/tmp` 再开就 OK。原因是 Windows 挂载的 NTFS 卷不支持 SQLite 的临时 WAL/journal 机制。解决方法：复制到容器内 `/tmp` 再操作

9. **bootstrapUsers 在编译后不工作**：容器启动后 `serve.ts` 的 `bootstrapUsers()` 函数虽然存在（grep 可见），但运行时 user 表始终为空，docker logs 无任何 `[bootstrapUsers]` 输出。原因未知（可能是 Bun compile 后的 Effect 层 provide 顺序问题，或 `console.log` 被吞掉）。临时绕道：用 Python 脚本手动插入用户
