# 智囊评审：opencode 多用户性能诊断报告

- 评审日期：2026-09-20
- 评审对象：`opencode-multiuser-perf-diagnosis.html`
- 评审方式：代码证据抽样核对（12 处引用全部实读源码验证）+ 多视角挑刺

## 方案概要

- 核心目标：定位 30 用户并发下页面加载慢的根因并给出分层修复方案
- 报告结论：SSE 全量广播（N² 放大）+ 持久事件逐条事务落在 Windows bind mount 卷（写串行排队）
- 修复分层：A 层配置（迁 DB 出 bind mount、清事件表、观测基线）→ B 层小改代码（SSE 按用户过滤、提监听器上限、Delta 节流）→ C 层架构演进（按用户分实例，现阶段不考虑）

## 专家视角

1. 资深后端架构师（事件驱动 / SSE 推送方向）
2. SQLite / 存储性能工程师
3. 安全审计员（多用户数据隔离面）
4. 魔鬼代言人（专找反例与实现陷阱）

## 评审意见

### 🔴 严重问题（必须在实施 B1 前解决）

**R1. B1 缺少"无归属事件白名单"设计，直接按 user_id 过滤会误伤正常事件流**

B1 说"只下发属于该用户的事件"，但事件流里存在大量无会话归属的事件，必须全员可达或按其他维度路由：

- `server.connected` / `server.heartbeat`（连接生命周期必需）
- `server.instance.disposed`（实例销毁通知，handlers/event.ts 专门监听它断开流）
- project / config / installation 级事件（如 `Installation.Event.Updated`）
- PTY 终端输出事件（`handlers/pty.ts` 存在，web 终端是高频事件源）

若过滤逻辑写成"session.user_id ≠ 当前用户就丢弃"，需要明确定义：哪些事件类型豁免过滤、哪些按 project 归属过滤。报告只提了"admin 全量"，粒度不够。这是 B1 落地时第一个会踩的坑。

**R2. B1 若按"sessionID 实时查库取归属"实现，会把卡点 2 恶化**

B1 给出两个归属获取方式之一："会话事件可由 sessionID 查归属"。如果在事件发布/分发热路径上每条事件查一次 session 表取 user_id，等于在已经拥堵的 SQLite 慢路径上，每事件追加一次读查询——广播延迟可能不降反升。

正确做法必须是**内存映射缓存**：会话创建/加载/变更归属时维护 `sessionID → userID` 的进程内 Map，事件分发只查内存。报告没有点明这一约束，属于会导致实施翻车的盲区。

（经核实：SessionShare 走外部 share-next 服务同步、生成公开 URL，被分享方不经本实例 SSE 收事件，因此 B1 不会造成分享功能回归——此风险排除。但 admin 跨用户查看会话的场景报告已正确覆盖。）

### 🟡 重要问题（影响分析的完整性与精度）

**R3. 漏了一个广播放大器：持久事件在 Bridge 被 emit 两次**

`event-v2-bridge.ts:42-66`：每条持久（sync）事件先 emit 一次原始事件，再 emit 一次 `{type:"sync", syncEvent:...}` 包装事件。即持久事件的实际扇出是 2N 而非 N。报告的 N² 结论不变，但图 2 的量化模型对持久事件占比高的场景低估了约一倍。

**R4. 重连风暴的标准解法（jitter + 放宽超时）被遗漏**

报告准确定位了卡点 4（15s 超时 vs 10s 心跳，余量仅 5s），但解决方案里没有对应项。标准修法是一行级改动：

- 客户端重连延迟从固定 250ms 改为**指数退避 + 随机抖动**（如 500ms~4s 随机），消除"所有标签页同步重连"的 thundering herd；
- `HEARTBEAT_TIMEOUT_MS` 从 15s 放宽到 30s+，给服务端繁忙时的心跳延迟留余量。

这应列为 B0，成本最低、见效最快，与 A1/B1 完全独立。

**R5. 客户端侧的卡顿成本被低估**

广播模式下每个浏览器每秒需 `JSON.parse` 全量 N×50 条事件（30 用户时约 1500 条/秒），再丢弃其中 29/30。浏览器主线程的 parse 开销本身就会造成页面卡顿——"加载慢"不全是服务端问题。这实际上进一步抬高了 B1 的优先级（B1 同时治好服务端 N² 和客户端 parse 风暴），报告只轻描淡写为"客户端再自行丢弃"。

**R6. "每次提交一次 fsync"的技术表述需修正**

`database.ts:30` 设置了 `synchronous = NORMAL`，WAL 模式下 commit 并非每次强制 fsync，fsync 主要发生在 checkpoint。准确的表述是：**WAL 的 write() 与 checkpoint 的 fsync 都要穿过 gRPC-FUSE 共享层**——write() 在该层同样是 RPC，结论方向不变，但评审要求技术表述精确。附带推论：写繁忙时 PASSIVE checkpoint 可能追不上 WAL 增长，与卡点 3（库膨胀）互为因果，值得在 A2 清理脚本里显式 `wal_checkpoint(TRUNCATE)`（报告 A2 已含，好）。

### 🟢 优化建议（锦上添花）

**R7. A2 清理 SQL 不完整**：`DELETE FROM event` 必须同时清 `event_sequence` 表（按 aggregate_id 关联），否则序列号表照样膨胀；且需说明语义——裸删 event 表不影响 session/message 投影表，但会影响事件 replay/审计追溯。

**R8. A 层可补充零风险 PRAGMA 调优**：`wal_autocheckpoint` 调大（降 checkpoint 频率）、`mmap_size`（WAL 下加速读）、`temp_store = MEMORY`。在 bind mount 上收益有限，但迁卷后叠加有效。

**R9. 验证清单可补一项客户端指标**：DevTools Performance 录制 30 用户场景下浏览器主线程的 JSON.parse 耗时占比，用于量化 R5。

## 苏格拉底质疑（请回应）

1. **"30 并发"是同时在线，还是同时活跃生成？** 图 2 假设每人 50 事件/秒仅在 LLM 流式输出时成立。若 30 人同时挂机的场景也慢，则卡点权重需要重排（重连风暴与 DB 读路径的权重上升）。建议先按 A3 采集真实活跃曲线再定 B3/B4 是否要做。
2. **为什么不是先 B0 再 A1？** 一行 jitter 改动能立刻切断"越慢越断"的正反馈，风险几乎为零，可能比迁卷更快让现网止血。
3. **数据暴露风险的定级是否太保守？** 其他用户的对话内容实时推送到每个登录浏览器，这是独立的水平越权安全漏洞（即使 UI 不展示，DevTools 可见）。从安全审计角度，B1 的驱动理由应改写为"安全修复，顺带解决性能"，优先级应提到性能论据之前。

## 风险预警

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| B1 过滤误伤无归属事件 → 前端状态不更新、实例销毁收不到 | 中 | 高 | R1 白名单先行；上线前用 R9 清单回归 |
| B1 热路径查库 → 写路径进一步恶化 | 中 | 高 | R2 强制内存映射，代码评审时作为硬性检查项 |
| A1 迁卷时 DB 拷贝不一致（容器未停干净/WAL 未 checkpoint） | 低 | 中 | 停容器→先 `wal_checkpoint(TRUNCATE)`→再拷贝；保留原目录备份一周 |
| 事件批量提交（如采纳 B4）引入崩溃窗口丢事件 | 中 | 中 | 窗口 ≤100ms、仅对持久事件、replay 校验已有（event.ts:279-319）可兜底 |

## 更优 / 报告未覆盖的方案

**B0 · 重连 jitter + 心跳超时放宽（新增，一行级，最先做）**
见 R4。切断正反馈循环的最低成本手段。

**B4 · 持久事件批量提交（新增，中期选项，替代部分 A 层收益）**
commitSyncEvent 当前每事件一个 `BEGIN IMMEDIATE` 事务。改为 50~100ms 窗口聚合同聚合的多条事件合并为一个事务，fsync/WAL 写入次数降一个数量级——这是从"次数"维度解卡点 2，A1 是从"单次成本"维度解，两者正交。可行性依据：流式 Delta 是临时事件不走 commit（实时性不受影响）；持久事件（Text.Ended、Tool.*）的 notify 延迟 100ms 用户无感知；seq 严格递增与 replay 校验逻辑可批量推广。风险与改动面大于 A1，建议 A1+B1 落地后若写路径仍是瓶颈再启动。

**A1 替代项 · WSL2 原生 docker-ce**
放弃 Docker Desktop，直接在 WSL2 发行版内装 docker-ce 运行同一镜像：bind mount 落在 ext4、无 gRPC-FUSE、无 Windows 端口代理（卡点 4 的"Docker Desktop 端口代理放大断连成本"也一并消除）。比 named volume 更彻底，运维形态不变，值得评估；若保留 Docker Desktop，则 named volume（报告 A1）是正解。

**B1 实现位置优化 · 订阅侧路由优于出口过滤**
报告方案在 SSE handler 出口处 filter——每条事件仍会被 EventEmitter 分发到全部 N 个监听器回调 + N 次 Queue.offer，只是省掉了 JSON.stringify 和 socket write。更优做法：连接建立时在监听器闭包上标记 userID，GlobalBus 封装一层按用户路由的 emit（或按 userID 分桶的子 Emitter），分发即定向。剩余的函数调用开销从 N² 降为 N。改动同样集中在 bus/global.ts + 两个 handler，不扩大上游冲突面。

## 评审结论

**⚠️ 有条件通过**

报告的问题分析正确、证据链经得起源码核对、分层思路合理，A 层（A1 迁卷）可直接执行。但 B1 作为核心修复，其实施设计存在两个会导致翻车的盲区（R1 白名单、R2 热路径查库），且漏掉了成本最低的正反馈止血手段（R4/B0）。

通过条件：

1. B1 实施前先定义**无归属事件白名单**（connected/heartbeat/disposed/project 级/installation 级），过滤条件 = `归属用户 == 当前用户 OR admin OR 白名单类型`
2. B1 归属判定**必须走进程内 `sessionID→userID` 内存映射**，禁止在事件热路径逐条查库；代码评审将其列为硬性检查项
3. 执行顺序调整为：**B0（jitter+超时放宽，立即）→ A1（迁卷）→ B1（按用户路由过滤）→ A2（清理，含 event_sequence）→ B2（监听器上限）**
4. 将数据暴露风险改写为 B1 的首要驱动理由（安全修复），同步更新报告相应章节
5. A1+B1 落地并采集基线后，若写路径仍饱和，再评估 B4（批量提交）与 C 层

核心理由：诊断部分已达到可行动质量；方案部分 A 层成熟，B 层方向正确但实现约束未闭合，补上 R1/R2/R4 三项后即可动工，不需要推翻重来。
