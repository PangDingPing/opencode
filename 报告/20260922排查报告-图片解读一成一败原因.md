# 排查报告：图片解读任务一成一败的原因

**日期**：2026-09-22（22:45 追加 PDF 会话排查）
**环境**：yejian-v0.1.7 容器（本机 192.168.3.21:8088），模型 GLM-5.3-Flash（scnet 国家超算互联网）

## 追加排查：PDF 会话 ses_f368a7b0fffei4wQoR9pdDiplG（22:45）

**会话内容**：用户上传 `1庞定平/排水系统图.pdf`（1 页，页面 3382×2395 pt 的 A1+ 大幅面图纸，文件 1.5MB），Read 工具报「PDF read successfully」，但模型 API 同样返回 HTTP 400 / code 10013。

**结论：还是受制于像素，不是 PDF 格式问题。** scnet 的 API 会把 PDF 页面按 **300 DPI 光栅化**成图片，然后套用同一条 72M 像素限制。该图纸页面 3382×2395 pt，按 300 DPI 渲染 ≈ 14092×9979 ≈ **1.4 亿像素**，超出限制近一倍。

验证实验（容器内直连 scnet API，用 OpenAI file content part 格式发送）：

| 实验 | 内容 | 结果 |
|---|---|---|
| 431 字节空白小 PDF（612×792pt） | ✅ 200，正确回答"空白文件" | → **PDF 格式本身支持** |
| 原始排水系统图.pdf | ❌ 400 / 10013 | 复现线上报错 |
| 同尺寸空白页（3382×2395pt，仅 433 字节） | ❌ 400 | → 与内容/体积无关，就是页面尺寸 |
| 半尺寸空白页（1691×1198pt） | ✅ 200 | |
| 空白页 2000×2000pt（=300DPI 下 69.4MP） | ✅ 200 | 精确定位阈值 |
| 空白页 2125×2000pt（=300DPI 下 73.9MP） | ❌ 400 | 阈值≈72MP，与图片路径完全一致 |
| 3.2MB 大体积 PDF 但页面缩到 600×600pt | ✅ 200 | → **PDF 体积大小不是限制** |

**PDF 页面尺寸安全上限**：宽×高 ≤ 约 4,147,000 pt²（等价于 72M 像素 ÷ 300DPI 的换算）。超出即 400。工程图纸常见的 A1（2384×3370pt ≈ 8.0e6 pt²）、A0 幅面**恰好都会超限**（A1 是 8.03e6，超限约 94%，属于边缘情况——实测同尺寸空白页是失败的；如需 A1 稳定通过，需按比例缩到 85% 以下）。

**修复建议（PDF 场景）**：`packages/opencode/src/tool/read.ts` 的 PDF 分支（L306~325）目前也是 base64 直传。建议发送前用 pypdf 读页面 MediaBox 尺寸，若 面积 > 约 4.1e6 pt²，先用 PIL/PyMuPDF 把页面光栅化并等比缩到 72MP 以内（或长边 8192）再作为图片发送。注意缩放渲染分辨率即可——图纸文字在长边 4096~8192 下识别效果依然良好。

## 原始排查：图片会话（22:29）

### 一句话结论

失败的会话上传的工程图纸 **排水系统图_00.png（9580×13528 ≈ 1.3 亿像素）** 超出了 scnet GLM-5.3-Flash 的**图片总像素上限 72,000,000 像素（72MP）**，接口直接返回 HTTP 400（错误码 10013「Invalid request parameters」），模型一个字都没输出。成功的会话图片只有 1152×864（约 100 万像素），远低于限制。

**统一规律（图片与 PDF 同源）**：scnet GLM-5.3-Flash 对视觉输入统一执行 72M 像素上限——图片按实际像素算，PDF 按 300 DPI 光栅化后的像素算。

## 验证实验（在容器内直连 scnet API 复现）

| 实验 | 图片 | 结果 |
|---|---|---|
| 对照组 | 小猫扑蝶.png 原图（1MP） | ✅ 200，正常描述 |
| 复现组 | 排水系统图_00.png 原图（129.6MP） | ❌ 400 / 10013，与线上报错一致 |
| 修复验证 | 同图缩至 1450×2048 | ✅ 200，正确识别为「A4栋 排水系统图」|
| 像素 vs 体积 | 9580×13528 但 JPEG 压到 4.3MB | ❌ 400 → 说明是**像素数**限制，不是请求体大小 |
| 像素 vs 体积 | 4000×4000 噪点图（payload 大） | ✅ 200 |
| 单边限制 | 4000×16000（单边 16000） | ✅ 200 → 单边长度不限 |
| 精确定位 | 71,995,225 px（8485×8485） | ✅ 200 |
| 精确定位 | 72,004,800 px（8400×8572） | ❌ 400 |

**限制精确为：width × height ≤ 72,000,000 像素（72MP）**，超出即报 400/10013，无论文件体积多小、单边多长。另测得 maxside=8192（47.5MP）时图纸识别效果良好。

## 修复建议

1. **短期（用户侧）**：大图先缩小再上传。工程图纸建议缩到长边 4096~8192，文字标注仍清晰可识别（实测 1450×2048 都能正确识别图纸内容）。
2. **根治（代码侧）**：`packages/opencode/src/tool/read.ts` 第 306~325 行，Read 工具读图后直接把原图 base64 内嵌为 data URL，无任何缩放。建议在 `isImage` 分支加预处理：解析 PNG/JPEG 头获取宽高，若 w×h > 约 70MP（留安全余量）则用容器内已有的 PIL（或 sharp）等比缩放后再编码。顺带建议对超大图统一限制到长边 ~8192，可以同时显著降低 vision token 成本（1MP 图就要约 1.4 万 input tokens）。
3. **体验（可选）**：模型 APIError 目前 UI 只表现为「无回复」，assistant 消息的 error 字段有完整信息但没有渲染出来；把 400 类错误提示给用户能减少「卡住了」的困惑。
